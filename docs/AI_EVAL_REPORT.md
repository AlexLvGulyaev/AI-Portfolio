## 🎯 1. Цель и объём

Документ фиксирует итоги приёмочного тестирования AI-ассистента портфолио: корректность ответов, latency, устойчивость к формулировкам и границы поведения.

Методика разделена по уровню доступа:

- **Функциональный benchmark** (174 теста/прогон) выполнялся **in-process на production-компонентах** (тот же код, конфигурация и KB, что обслуживают public-трафик), что позволяло сверять ответы с внутренним состоянием retrieval и промпта.
- **Публичный HTTP API `POST /chat`** использовался для smoke-проверок и измерения latency на production cache-miss (включая сетевой и сериализационный overhead).
- Кейсы инъекций (класс L) выполнялись на **изолированных fixtures**, а не на production-документах: production-корпус не подвергался риску контаминации.

Вмешательства в работу обычных пользователей не было.

Полный диагностический набор (174 теста, трассировки, production-снимки) хранится приватно и не публикуется. В публичный репозиторий вынесен только обезличенный [regression set](../backend/tests/ai_portfolio_eval_set.json) (§6).

## 📐 2. Методика

Тесты разбиты на классы по типу проверяемого поведения:

| Класс | Что проверяет |

| M | Устойчивость к формулировкам: опечатки, регистр, краткая форма |

Особенности оценки:

- Проверки выполнялись по структурированным критериям (наличие ожидаемых фактов, полнота перечисления, маркеры отказа), без «суждения модели о модели».
- Ответы класса C сверялись с допущенными документами KB: факт засчитывался только если он присутствует в документах соответствующего проекта.
- Корректность и latency измерялись на production cache-miss (кеш реальных ответов ассистента), многократно — для отделения систематических дефектов от стохастических колебаний генерации.
- Дефекты, найденные кампанией, исправлялись итеративно; финальные цифры — по последнему прогону на финальном коде.

## 🔁 6. Regression set

Публичный контрольный набор: [`backend/tests/ai_portfolio_eval_set.json`](../backend/tests/ai_portfolio_eval_set.json) — 24 вопроса, покрывающих классы A/B/C/D/E/F/H/M. Первый прогон и принятый результат — 29.08.2026 (см. §9).

**Что в наборе:** собственные контрольные вопросы и ожидания, основанные на публичной информации витрины (реестр проектов, публичная документация кейсов).

**Чего в наборе нет:** production-данных (UUID сессий, диалогов посетителей), трассировок, adversarial-кейсов (инъекции через документы, попытки раскрытия системного промпта) — они хранятся приватно.

### Запуск

```python
#!/usr/bin/env python3
"""Прогон публичного regression set на развёрнутом экземпляре проекта.

По умолчанию — локальный инстанс (http://localhost:8000).
Production-адрес задаётся ТОЛЬКО явно, через переменную окружения AIP_BASE_URL.
"""
import json, os, uuid, requests

BASE = os.environ.get("AIP_BASE_URL", "http://localhost:8000")
SET = json.load(open("backend/tests/ai_portfolio_eval_set.json", encoding="utf-8"))
MARKERS = SET["refusal_markers"]

def check(answer: str, c: dict) -> list[str]:
    low = answer.lower()
    errs = []
    if len(answer) < c.get("min_chars", 0):
        errs.append(f"too short ({len(answer)} < {c['min_chars']})")
    for s in c.get("mentions_all", []):
        if s.lower() not in low:
            errs.append(f"missing: {s}")
    any_min = c.get("mentions_any_min")
    if any_min:
        hits = sum(1 for s in c["mentions_any"] if s.lower() in low)
        if hits < any_min:
            errs.append(f"mentions {hits}/{any_min} from mentions_any")
    for s in c.get("not_mentions", []):
        if s.lower() in low:
            errs.append(f"must not mention: {s}")
    if c.get("refusal") and not any(m in low for m in MARKERS):
        errs.append("expected refusal marker")
    return errs

# Уникальный visitor_id на каждый запуск: прогон не смешивается
# с данными других запусков и с трафиком реальных посетителей.
visitor_id = f"regression-{uuid.uuid4()}"
groups: dict[str, str] = {}   # общая сессия — только для явных session_group
failed = 0
for t in SET["tests"]:
    group = t.get("session_group")
    # ВАЖНО (найдено дебагом 29.08.2026): /chat валидирует переданный
    # session_id и при отсутствии такой сессии создаёт новую — клиентский
    # идентификатор игнорируется. Диалоговую группу нужно «заякорить»:
    # первым вызовом без session_id получить серверный id и использовать
    # его в последующих вызовах группы.
    session = groups.get(group) if group else None
    r = requests.post(f"{BASE}/chat", json={
        "message": t["question"], "session_id": session, "visitor_id": visitor_id,
    }, timeout=60)
    r.raise_for_status()
    data = r.json()
    if group and not session:
        groups[group] = data["session_id"]  # якорь сессии группы
    answer = data["answer"]
    errs = check(answer, t["check"])
    status = "PASS" if not errs else "FAIL: " + "; ".join(errs)
    failed += bool(errs)
    print(f"[{t['id']}] {status}")

print(f"\n{len(SET['tests']) - failed}/{len(SET['tests'])} PASS")
```

Замечания к прогону:

- runner по умолчанию бьёт в `http://localhost:8000`; адрес production задаётся только явной переменной окружения `AIP_BASE_URL`;
- `visitor_id` уникален на каждый запуск — данные прогона не смешиваются с другими запусками и реальным трафиком;
- тесты одной `session_group` выполняются с общим `session_id` (проверка диалога); тесты без `session_group` — каждый со своей независимой сессией;
- сессия диалога якорится сервером: первый вызов группы идёт без `session_id`, для последующих используется возвращённый `session_id` (см. комментарий в раннере выше);
- HTTP-ошибки останавливают тест с диагностируемым исключением (`raise_for_status`), а не превращаются в ложный FAIL;
- тесты класса E проверяют консистентность: два одинаковых вопроса реестра должны давать одинаковый детерминированный ответ;
- набор не является полной проверкой: он покрывает ключевые классы поведения и служит быстрой регрессией после изменений промпта, retrieval или состава KB. После изменения KB или системного промпта ожидается повторный полный приёмочный прогон (приватный).

## 🧮 10. Эксперимент «размер чанка × retrieval-бэкенд» + класс «грязных» вопросов (31.08.2026)

Контекст. 30.08.2026 чанковка KB переведена на **heading-aware**: разрез корпуса по заголовкам markdown-документов, атомарная секция ≤ `chunk_size` становится самостоятельным чанком, скользящее окно сохраняется только для секций-«переростков». Причина: чанки фиксированного окна 900/120 «разбавляли» узкие секции FAQ/глоссария (контактный блок FAQ длиной 254 символа сидел внутри 900-символьного чанка с косинусом 0,33 против 0,45 у лидеров топ-6; изолированная секция давала бы 0,65) — из-за этого ассистент честно отказывался на вопросы, ответы на которые в корпусе есть. Одновременно исправлен дефект конвертера markdown→plain (мусорные `>` от HTML-тегов в тексте чанков). Ресинк: 230 документов / 14 источников / **7656 чанков** (было 3285 на окне без заголовочной структуры).

**Важно о сопоставимости:** все принятые прогоны §3, §8 и §9 прошли на корпусе со «старой» нарезкой — в момент этих тестов heading-aware чанковки не существовало. Абсолютные уровни этого эксперимента напрямую не сравнимы с ними; сравнимы между собой — четыре ячейки ниже (один код, один корпус, один режим кеша).

Метод по каждому прогону: полный regression set (классы A–M, 168 тестов) + новый класс X (8 «грязных» пользовательских формулировок: без пунктуации, с опечатками, транслит, два-в-одном, размытые деловые фразы) = 176 тестов через живой пайплайн; кеш ответов — свежий, без сидирования (HIT только на штатных повторах внутри прогона); изолированные eval-визиторы. Корпус — общий для всех ячеек (синк 30.08); хранилища — изолированные коллекции chroma и классы weaviate в тех же инстансах, производственные не затронуты; сверка «создано vs сохранено» и постатейная сверка с эталонной коллекцией — 0 расхождений.

### Результаты (по одному прогону на ячейку)

| Ячейка | Класс C (из 77) | Итог без кеш-класса J (из 176) | p95 класса C, мс |
|--------|-----------------|--------------------------------|------------------|
| Chroma 900/120 (принятая конфигурация) | **64** | **160 (90,9%)** | **2212** |
| Chroma 1400/250 | 61 | 157 (89,2%) | 2290 |
| Weaviate 900/120 | 61 | 156 (88,6%) | 2380 |
| Weaviate 1400/250 | 64 | 159 (90,3%) | 2515 |

Класс X («грязные» вопросы): 5/8 · 5/8 · 4/8 · 5/8 во всех ячейках.

### Выводы

- **Увеличение чанка до 1400/250 выигрыша не даёт** ни на одном бэкенде: класс C и итоговый счёт либо равны базе, либо ниже в пределах шума одиночного прогона; p95 не улучшается. При heading-aware нарезке параметр 900 ограничивает только секции-переростки, и принятая конфигурация **900/120 (chroma) сохраняется без изменений**.
- **Бэкенд-паритет подтверждён на полном контуре weaviate** (собственная индексация, а не копирование векторов, как в §8): идентичные корпуса дают эквивалентное качество.
- Структура провалов класса C одинакова во всех ячейках: ~10 тестов падают всюду (нужные якорные тексты недостижимы или отсутствуют в корпусе — вопрос полноты KB, а не чанкинга), остальные 3–6 переключаются стохастически. Класс X устойчиво показывает зону роста в понимании фразы, а не в retrieval: в трети случаев ассистент отвечает уточнением-отказом вместо полезного ответа на размытую/эмоциональную формулировку. Обе зоны — отдельные итерации, не связанные с размером чанка.
- Попутно найден и локализован **латентный дефект weaviate-стенда**: text-свойства индекса создаются с дефолтной токенизацией `word`, из-за чего фильтр удаления по `document_id` на токенизированном поле захватывает чужие документы (те, чьи пути распадаются на то же множество токенов) — реиндексация молча теряла ~3% корпуса без единой ошибки. Для текущего прода риска нет (активен chroma, удаление точное); до любого переключения активного бэкенда на weaviate требуется фикс токенизации свойств и пересоздание классов.

Ограничение: один прогон на ячейку — разница в 1–4 теста статистически не отделяется от стохастики модели; строгий повторный прогон возможен при принятии решения об изменении конфигурации. Артефакты прогонов хранятся приватно (§1).

### Дополнение (31.08.2026, день тот же): малые чанки 500/50 и 600/100 + разбор латенси

Для полноты тренда матрица достроена влево: 500/50 (исторический размер до 29.08) и 600/100 на обоих бэкендах — ещё 4 изолированных хранилища и 4 полных прогона по 176 тестов (итого 8 ячеек / 1408 вызовов). Реиндексация: 500/50 → 9282 чанка, 600/100 → 8645 (при 1400/250 — 7279); создано vs сохранено — 0 расхождений во всех хранилищах.

| Ячейка | Класс C (из 77) | Итог без J (из 176) | p95 класса C, мс |
|--------|-----------------|---------------------|------------------|
| Chroma 500/50 | 65 | 159 (90,3%) | 2159 |
| Weaviate 500/50 | 66 | 160 (90,9%) | 2412 |
| Chroma 600/100 | 66 | 161 (91,5%) | 2234 |
| Weaviate 600/100 | 63 | 159 (90,3%) | 2661 |

Средние по размерам чанка (по двум бэкендам): C — 500 → 65,5 · 600 → 64,5 · 900 → 62,5 · 1400 → 62,5; итог — 500 → 159.5 · 600 → 160 · 900 → 157.5 · 1400 → 157.5. Лёгкий перевес малых чанков однонаправленно на обоих бэкендах, но амплитуда 2–3 теста на границе шума одиночного прогона — для смены конфигурации оснований нет, рабочая **900/120 (chroma) сохраняется**. Структура провалов класса C стабилизировалась: **9 тестов падают в 7–8 ячейках из 8** (якорные тексты недостижимы/отсутствуют в корпусе), ещё 11 переключаются стохастически.

Разбор латенси по стадиям (из трасс всех 8 прогонов, без кеш-попаданий): **размер чанка на латенси не влияет** — retrieval p50 136–177 мс и p95 174–297 мс одинаков во всей вилке 500–1400, объём генерации не растёт (средняя длина ответа 485–501 знак, ~4 источника в контексте всюду). Доминирует генерация (85–90% времени, p50 ~1,2 с — скорость LLM). Единственный систематичный фактор — бэкенд: **chroma стабильно быстрее weaviate на p95 на ~100–450 мс** во всех парах (класс C p95: 2159–2290 против 2380–2661 мс); оба далеко внутри критерия 5000 мс, резервный бэкенд остаётся пригодным.
