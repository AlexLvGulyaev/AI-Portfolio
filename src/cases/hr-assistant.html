HR Assistant — LoRA Fine-Tuning

LoRA Qwen Fine-Tuning ML
GitHub Demo

Постановка проблемы

HR-ассистент должен решать, подходит ли кандидат на вакансию, и выдавать структурированный JSON с оценкой и обоснованием.

Базовая модель Qwen2.5-1.5B-Instruct сразу выдавала валидный JSON, но принимала плохие matching-решения: например, соглашалась, что врач подходит на вакансию Prompt Engineer. Валидный формат ответа ещё не означал правильного ответа.

  • Valid JSON: 100%, но точность решений — 44%.
  • Perplexity и validation loss не предсказывали качество бизнес-логики.
  • Нужно было научить модель смыслу, а не только формату.

Почему LoRA

Вместо того чтобы полагаться на облачный API, был выбран локальный LoRA-адаптер над Qwen2.5-1.5B-Instruct. Это дало контроль над данными, моделью и процессом обучения, позволило многократно итерировать датасет и воспроизводить результаты.

  • Контроль. Teacher dataset собирался из собственной базы prompt evaluation, а не из публичных источников.
  • Итеративность. Адаптер обучается за ~3 минуты на одном GPU — можно быстро проверять гипотезы о данных.
  • Честная оговорка. Скорость и экономия не были начальными преимуществами; latency стала отдельной инженерной задачей.

Четыре эксперимента

Каждый эксперимент отвечал на вопрос, оставленный предыдущим. Гиперпараметры адаптера оставались фиксированными; менялся только состав teacher dataset.

Exp 001 — Baseline 90 записей. LoRA не улучшила решения, хотя eval loss упал до 0.23.
Exp 002 — Тюнинг ёмкости 90 записей. Accuracy выросла до 78%, но hard negatives всё ещё проходили.
Exp 003 — Hard negatives 123 записи. Negative smoke заработал, но модель стала консервативной.
Exp 004 — Баланс 162 записи. Positives и borderlines вернули recall; external validation 93.1%.

Эволюция точности решений

Точность matching-решений росла неравномерно: 44% → 78% → 67% → 80%. Падение на Exp 003 — осознанная жертва recall ради устойчивости к hard negatives.

Рис. 1. Decision accuracy: Base Qwen vs LoRA по четырём экспериментам.

Состав датасета влиял на качество решений сильнее, чем ёмкость адаптера. Experiment 001 имел самый низкий validation loss, но худшие решения — ключевое доказательство того, что loss не является целевой метрикой для этой задачи.

Эволюция ошибки оценки

Средняя абсолютная ошибка композитного score снизилась с 38 до 15 баллов. Base model ошибался сильнее всех; Exp 004 достиг минимальной MAE на тестовой выборке.

Рис. 2. MAE score: Base Qwen vs LoRA по четырём экспериментам. Меньше — лучше.

Ошибка score уменьшалась по мере улучшения примеров, а не по мере понижения loss. Это подтверждает главный инженерный вывод: инженерия датасета важнее тюнинга адаптера.

External validation

На 102 независимых парах кандидат–вакансия LoRA достигла 93.1% decision accuracy против 94.1% у GPT-4o-mini. Модель обобщается, но score калибруется не идеально.

Рис. 3. External validation scatter: LoRA score против reference score. Точки вблизи диагонали означают хорошую калибровку.

Telegram Production Smoke

Offline-метрики неэквивалентны production-качеству. Runtime smoke на реальном API выявил failure modes, которых не было в тестовой выборке.

Рис. 4. Production smoke matrix: positive, obvious negative, hard negative, edge case, invalid input, stability repeat.

Experiment 002 провалил negative-кейсы на реальном API; hard negatives в Experiment 003 устранили это. В процессе evaluation также был найден production-баг: truncated JSON при max_tokens=300 вызывал HTTP 422. Фикс — увеличение лимита до 512 и graceful JSON extraction — вернул 100% valid JSON.

Dataset Engineering

Рост качества шёл за счёт инженерии датасета, а не адаптера: 90 → 123 → 162 записи. Hard negatives устранили false positives, positives и borderlines вернули recall.

Рис. 5. Эволюция teacher dataset: записи по классам и split в каждом эксперименте.

Гиперпараметры LoRA оставались неизменными на протяжении всех четырёх экспериментов. Единственная систематически меняющаяся переменная — состав и баланс teacher dataset. Это делает датасет доминирующим фактором качества.

Итоговые выводы

Четыре эксперимента и финальное Telegram-расследование привели не только к работающей модели, но и к чёткому пониманию границ: что доказано, что частично доказано и что требует следующего цикла.

✓ Доказано

Инженерия датасета важнее тюнинга адаптера. Hard negatives и positives/borderlines — рабочие рычаги качества. Технический контур и deployment воспроизводимы.

~ Частично доказано

93.1% decision accuracy на external holdout и 100% production smoke pass. Hard-negative качество в реальных сценариях требует дополнительной stratified evaluation.

→ Next cycle

Калибровка score, уменьшение latency, расширение teacher dataset и добавление hard-negative метрик в валидационный pipeline.
